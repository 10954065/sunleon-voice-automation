# Database Design — Sunleon Voice

## Status

Phase 1 + Phase 2 schema implemented (auth/orgs/roles, plus Agent Studio and the knowledge base). Phase 3+ models (Conversation, Lead, UsageEvent, Plan, Subscription) are sketched at the bottom as forward-looking plan, **not implemented**.

## Provider

PostgreSQL, via Prisma. See `docs/DECISIONS.md` for why Postgres-from-day-one rather than SQLite-then-migrate.

## Phase 1 schema

### `User`
Authentication identity. One row per person, independent of any organization.

| Field | Type | Notes |
|---|---|---|
| id | String (cuid) | PK |
| email | String | unique |
| passwordHash | String? | null if the user only ever signs in via a future OAuth provider |
| name | String? | |
| createdAt / updatedAt | DateTime | |

### `Organization`
A tenant / workspace.

| Field | Type | Notes |
|---|---|---|
| id | String (cuid) | PK |
| name | String | |
| slug | String | unique, used in dashboard URLs |
| createdAt / updatedAt | DateTime | |

### `Membership`
Join table binding a `User` to an `Organization` with a role. **This is the row every tenant-scoped query must check.**

| Field | Type | Notes |
|---|---|---|
| id | String (cuid) | PK |
| userId | String | FK → User |
| organizationId | String | FK → Organization |
| role | Enum `Role` | `SUPER_ADMIN`, `OWNER`, `ADMIN`, `AGENT_MANAGER`, `ANALYST` |
| createdAt | DateTime | |

Unique constraint on `(userId, organizationId)` — one role per user per org.

### `AuditLog`
Append-only record of security-relevant events.

| Field | Type | Notes |
|---|---|---|
| id | String (cuid) | PK |
| organizationId | String? | null for platform-level events (e.g., registration before an org exists) |
| actorUserId | String? | who did it |
| action | String | e.g. `org.created`, `member.invited`, `member.role_changed`, `auth.login`, `auth.login_failed` |
| metadata | Json? | event-specific detail, never secrets |
| createdAt | DateTime | |

### Auth.js tables (`Account`, `Session`, `VerificationToken`)
Standard Auth.js/Prisma-adapter tables for session and (future) OAuth account linking. Not hand-rolled — generated by the Prisma adapter's required schema.

## Multi-tenancy enforcement

Every tenant-owned table carries `organizationId`. The application never accepts a client-supplied `organizationId` as authoritative — it is always re-derived server-side from the caller's `Membership` rows (see `docs/ARCHITECTURE.md` → request flow, and `docs/SECURITY_MODEL.md`). Row-Level Security was considered and deferred: application-level scoping was chosen for Phase 1 because the whole stack (one Next.js app, one Prisma client) already funnels every tenant query through the same helper functions, and RLS policies would add operational complexity (role-switching per request, policy drift vs. Prisma schema) without a second access path (e.g., direct SQL from another service) to justify it yet. This should be revisited if a non-Prisma access path to the database is ever introduced.

## Indexes / constraints (Phase 1)

- `User.email` — unique index.
- `Organization.slug` — unique index.
- `Membership(userId, organizationId)` — unique composite index.
- `Membership.organizationId` — index (every dashboard query filters by this).
- `AuditLog.organizationId, createdAt` — composite index for time-ordered audit queries.

## Phase 2 schema (implemented)

### `Agent` / `AgentVersion`
Versioned so live conversations (Phase 3) won't be affected by in-progress edits. `Agent.publishedVersionId` points at whichever `AgentVersion` is currently live; the latest version with `publishedAt = null` (if any) is the draft being edited. Publishing sets `publishedAt` and repoints `publishedVersionId`; rollback just repoints `publishedVersionId` to an older already-published version — it never mutates history.

| Field (`AgentVersion`) | Type | Notes |
|---|---|---|
| agentId | String | FK → Agent |
| versionNumber | Int | unique per agent, increasing |
| instructions | String | required |
| persona / tone / greeting | String? | optional |
| languages | String[] | defaults to `["en"]` |
| leadCaptureEnabled | Boolean | |
| publishedAt | DateTime? | null = draft |

### `KnowledgeSource` / `KnowledgeChunk`
`KnowledgeSource` tracks one FAQ/manual-text/website-URL/file upload per agent, with a `status` lifecycle (`PENDING → PROCESSING → READY` or `FAILED`, with `errorMessage` set on failure). `KnowledgeChunk` holds the post-chunking text plus its embedding.

The `embedding vector(1536)` column on `KnowledgeChunk` is **not a normal Prisma-managed column** — see `docs/DECISIONS.md` for why (Prisma's classic schema generator has no native pgvector type) and the mandatory operational rule for running migrations on this project (never run bare `prisma migrate dev`). It's declared `Unsupported("vector(1536)")` in `schema.prisma` purely so drift detection doesn't try to drop the column; it's read/written only via `$queryRaw`/`$executeRaw` in `src/server/knowledge/retrieval.ts`. An HNSW cosine-distance index backs the similarity search.

Both tables carry `organizationId` **and** `agentId`, and every retrieval/mutation query filters on both — not just the source/chunk id — mirroring the Phase 1 tenant-isolation pattern. See `tests/integration/knowledge.test.ts` for the test proving a query scoped to Org A never returns Org B's chunks even when both exist.

## Phase 3+ schema sketch (NOT IMPLEMENTED)
